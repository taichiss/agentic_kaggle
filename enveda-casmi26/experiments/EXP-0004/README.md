# EXP-0004: PubChemLite を候補 pool に足すときのマイナス面

- **日付:** 2026-10-28
- **コード:** `scripts/casmi26_baseline_cv.py --extra-pool pubchemlite` (EXP-0003 で追加)
- **問い:** PubChemLite で候補が増えると、正解が薄まって上位 25 本に残らなくなるか
- **LB:** 新規提出なし

## 結果 (A = 3 チャネル固定融合、B = analog 単独)

| 条件 | 候補数 (中央値) | A なし → あり | B なし → あり | カバー率 |
|---|---:|---:|---:|---:|
| NP Class 2 (keep) | 53 → 87.5 | 0.194 → 0.183 (−0.011) | 0.535 → 0.511 (−0.024) | 99.6% → 99.2% |
| NP Class 1 (other) | 53 → 87.5 | 0.914 → 0.909 (−0.004) | 0.638 → 0.624 (−0.013) | 99.6% → 99.2% |
| fold0 Class 2 (drug-like) | 88 → 113.5 | 0.096 → 0.094 (−0.002) | 0.598 → 0.592 (−0.006) | 100% → 100% |
| NP pool 外 (drop、EXP-0003) | — → 88 | 0.004 → **0.175** | 0.009 → **0.488** | 3.2% → **96.0%** |

NP Class 2 の内訳:
- 窓のうち PubChemLite 由来は 21.5%。25 本を超える候補がある分子は 71% → 84%
- A で正解の順位が下がったのは 66 分子、上がったのは 7 分子。上位 25 本に正解が入る分子は 191 → 185、1 位は 18 → 16
- 誤答 1 位が PubChemLite 由来だった割合: A 0.9%、B 14.5%。PubChemLite の候補はライブラリのスペクトルを持たないので、ライブラリ一致に引っ張られる A では上位に来にくい
- カバー率の −0.4% (1 分子) は、予備窓 (±30 ppm) が「±8.5 ppm 窓が空のときだけ」働く作りのため (EXP-0003 README 参照)

計算コスト: 検索後の処理 (正規化と断片列挙) が fold0 で約 2 倍 (23 → 52 秒、90 → 189 秒、12 コア)。Kaggle の 4 コアでは、全体 28 分に対して +5〜7 分程度の見込み。必要なファイルは meta と mass だけ (計 27 MB)

## LB への正味の効果 (EXP-0002 のクラス構成で試算、未検証)

ΔLB ≈ p1·Δ(Class 1) + p2·Δ(Class 2) + p3·r·M(救済後)、p1 = 0.148、p2 = 0.285、p3 = 0.567

- r は「pool 外の分子のうち、PubChemLite に正解が入っている割合」(hidden test では未知)
- A: ΔLB ≈ −0.004 + 0.099·r → **r ≈ 4% で損益分岐**、r = 30% なら +0.026
- B: ΔLB ≈ −0.009 + 0.277·r → **r ≈ 3% で損益分岐**、r = 30% なら +0.074

## 結論

- 「25 本に絞れなくなる」ことは起きない。ランカーは常に上位 25 本を出し、もともと 7 割の分子で候補は 25 本を超えていた。問題になるのは正解の順位が少し下がる「希釈」で、その損は Class 1/2 とも −0.002〜−0.024 と小さい
- pool 外の分子の数% でも救えれば元が取れる。NP では 96% を救えた
- 対策: 予備窓の発動条件の見直し、候補の出どころ (COCONUT / train / PubChemLite) を特徴量に入れる、PubChem の popularity prior で希釈を抑える

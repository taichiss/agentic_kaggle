# Pull Request ガイドライン

## 原則

- 1 PR は 1 つの責務またはレビュー観点に限定する。
- プラットフォーム変更と単一コンペの実験変更を、理由なく同じ PR に混ぜない。
- Accepted ADR を変更する設計は、新しい ADR と実装をレビュー可能な順序に分ける。
- ユーザー指示がない限り `main` へ直接 push、force push、merge をしない。
- 生データ、モデル、予測、提出物、secret を含めない。
- 実行していない検証を成功と記載しない。

## PR 本文

少なくとも次を含めます。

1. 目的・背景
2. 変更内容
3. 設計理由と関連 ADR
4. 受入条件との対応
5. 対象外・残課題
6. 検証結果
7. コンペ、データ、スコアへの影響
8. レビューしてほしい点

構造、依存関係、データフローの変更は Mermaid で図示します。E2E を記載する場合は、使用した
データ種別、入口と出口、設定、件数、未確認ケースを明記します。

## 作成前チェック

- [ ] 関連 ADR と Issue の最新情報を確認した
- [ ] platform と competition の境界を守っている
- [ ] 実験結果と戦略文書を同期した
- [ ] 標準検証の実際の結果を記載した
- [ ] `git status` と `git diff` を確認した
- [ ] データ、生成物、secret が含まれていない
